# Библиотека FastAPI

Проект для управления библиотечным каталогом, реализованное с использованием FastAPI.

## Описание проекта

Проект это REST API для управления библиотечным каталогом.
Он позволяет выполнять основные операции CRUD (создание, чтение, обновление, удаление) для книг.
Работа с проектом может производиться двумя способами с помощью хранилища данных JsonBin.io  и файла JSON, 
или  с базой данных Postgresql.

## Функциональность

- Получение списка всех книг с возможностью фильтрации
- Получение информации о конкретной книге
- Добавление новой книги в каталог
- Обновление информации о книге
- Удаление книги из каталога

## Модель данных

Каждая книга содержит следующие данные:

- id (уникальный идентификатор)
- название
- автор
- год издания
- жанр
- количество страницs
- доступность (в наличии/выдана)
- обложка
- описание
- рейтинг

## Установка и запуск 


1. Клонировать репозиторий
2. Создать виртуальное окружение и активировать его
   ```
   python -m venv .venv
   source .venv/bin/activate
   ```
3. Установить зависимости:
   ```
   pip install -r requirements.txt
   ```
4. Заполнение .env файла
   создать копию .env.example

5. Запустить приложение:

   Работа с хранилищем JsonBin.io и файлом JSON:
   ```
   python -m app.library_catalog.main
   ```
   
   Работа с базой данных Postgresql:
   ```
   python -m app.db.main_db
   ```
   
6. Открыть Swagger UI по адресу http://127.0.0.1:8000/docs

## Анализ способов хранения данных

### 1. Хранение данных в оперативной памяти

**Плюсы:**
- Высокая скорость доступа и обработки данных
- Простая реализация
- Не требует внешних сервисов или баз данных

**Минусы:**
- Все данные исчезают при перезапуске приложения
- Ограничены объёмом доступной оперативной памяти
- Не масштабируемо: каждый экземпляр приложения хранит собственную копию данных
- Нет возможности автоматически восстанавливаться или создавать резервные копии
- Возможны потери или несогласованность данных при сбоях

**Ключевые особенности:**
- Нет поддержки атомарных операций и транзакций
- В случае нескольких запущенных экземпляров — данные не синхронизированы, что усложняет масштабирование
- Не реализованы механизмы обеспечения целостности данных

---

### 2. Хранение в JSON-файлах

**Плюсы:**
- Простая и быстрая реализация
- Данные сохраняются между перезапусками
- Легко читаемы и редактируемы вручную
- Не требуют сложной инфраструктуры или внешних баз данных

**Минусы:**
- Снижение производительности при больших объёмах данных
- Нет встроенных механизмов поиска или индексации
- Отсутствие транзакционной поддержки
- Возможны гонки при одновременных обращениях
- Повреждение данных при неправильной записи или сбоях

**Особенности конкурентного доступа:**
- Одновременные операции могут приводить к потере данных
- Без блокировок возможны конфликты при одновременной записи
- Каждая операция часто предполагает чтение и перезапись файла, что снижает эффективность
- В случае сбоя во время записи — данные могут быть испорчены

---

### 3. Хранение в базе данных (SQL или NoSQL)

**Плюсы:**
- Поддержка транзакций и соблюдение ACID
- Высокая скорость и масштабируемость
- Возможность проводить сложные запросы
- Управление правами доступа
- Автоматическое резервное копирование и восстановление данных
- Индексация для быстрого поиска
- Обеспечение целостности и согласованности данных

**Минусы:**
- Более сложная настройка и управление инфраструктурой
- Требует определения схемы (для SQL)
- Увеличение сложности развертывания
- При неправильной настройке — возможный спад производительности
- Требуются дополнительные системные ресурсы

## Вывод

Каждый способ хранения данных обладает своими сильными и слабым сторонами, и окончательный выбор зависит от специфики проекта и его требований:

1. **Оперативной памяти** отлично подходит для быстрых прототипов, тестовых систем или случаев, когда важна только временная работа с данными, без необходимости их сохранения после завершения работы программы.

2. **JSON-файлов** хорошо работает в небольших и менее нагруженных приложениях, где нужен простой механизм хранения данных и достаточно низкие требования к скорости и масштабируемости. Однако при росте объема данных или увеличении нагрузки возникает риск потери эффективности.

3. **Базами данных** — это оптимальный вариант для корпоративных, производственных систем, где требуется высокая надежность, масштабируемость и возможность работы с большим количеством одновременных пользователей. Благодаря встроенным механизмам транзакций и свойствам ACID базы данных обеспечивают целостность и согласованность данных даже при конкуретных операциях.
